# Custom Elements Manifest — Post-Implementation Checks

Run every check below **after** wiring a Custom Elements Manifest into a
web-component package, and **before** declaring the work done.

Each check: what to look for, how to verify, what failure looks like.
Failing any check means the work is not complete. Mark each as ✅ pass,
❌ fail, ⚠️ exception (with reason), or N/A in the PR description.

Read [custom-elements-manifest.md](./custom-elements-manifest.md) for
rationale and
[custom-elements-manifest.decisions.md](./custom-elements-manifest.decisions.md)
for the matching decision tags.

Each check is tagged **`[auto]`**, **`[semi]`**, or **`[manual]`** —
see [css-structure.checks.md](./css-structure.checks.md) for the
meaning of each tier.

> **Applicability gate (D-CEM-1).** This whole triad is **N/A** for
> Svelte / light-DOM components that don't call
> `customElements.define(...)`. The `.checks.sh` script detects the
> absence of a `customElements.define` call and skips every check with
> an N/A note. Dual-build packages (D-CEM-1 = C) are treated as
> web-components here.

Paths below assume a single-package repo (`custom-elements.json` at the
package root). For a monorepo, substitute the package path
(`packages/<component>/…`).

---

## C-CEM-1 — Analyzer + integration packages are devDependencies

**Tier:** `[auto]`

**What:** `@custom-elements-manifest/analyzer` and the two editor
integration packages (`custom-element-vs-code-integration`,
`custom-element-jet-brains-integration`) are present in
`devDependencies`.

**How to verify:**
```bash
node -e "const d=require('./package.json').devDependencies||{}; \
  ['@custom-elements-manifest/analyzer','custom-element-vs-code-integration','custom-element-jet-brains-integration'] \
  .forEach(p=>console.log(p, p in d ? 'ok' : 'MISSING'))"
```

**Pass:** All three present.

**Failure mode:** `cem analyze` isn't runnable; the artifacts can't be
regenerated and go stale.

**Tag:** D-CEM-3.

## C-CEM-2 — Analyzer config file exists at the package root

**Tier:** `[auto]`

**What:** A `custom-elements-manifest.config.{mjs,js,cjs}` file exists
and wires in the VS Code + JetBrains plugins (per D-CEM-3 = A).

**How to verify:**
```bash
ls custom-elements-manifest.config.* 2>/dev/null
```

**Pass:** One config file present. (If D-CEM-3 = B, the editor files
are generated by separate scripts — mark ⚠️ and confirm those scripts
run under `build`.)

**Failure mode:** No single source of truth for generation; editor
files drift from the manifest.

**Tag:** D-CEM-3.

---

## C-CEM-3 — `custom-elements.json` exists at the package root

**Tier:** `[auto]`

**What:** The manifest file is present (post-build).

**How to verify:**
```bash
test -f custom-elements.json && echo ok || echo missing
```

**Pass:** The file exists.

**Failure mode:** No manifest → no webcomponents.org listing, no editor
integration. This is the artifact everything else points at.

**Tag:** D-CEM-2.

---

## C-CEM-4 — `package.json` `customElements` field points at the manifest

**Tier:** `[auto]`

**What:** `package.json` has a `"customElements"` field and it resolves
to an existing file.

**How to verify:**
```bash
node -e "const p=require('./package.json'); const f=p.customElements; \
  console.log(f ? (require('fs').existsSync(f)?'ok '+f:'DANGLING '+f) : 'FIELD MISSING')"
```

**Pass:** Field present and the referenced file exists.

**Failure mode:** The single most important field is missing —
webcomponents.org's validity check and VS Code's package auto-discovery
both key off it. Without it there is no listing.

**Tag:** D-CEM-2.

## C-CEM-5 — `package.json` `web-types` field points at `web-types.json`

**Tier:** `[auto]`

**What:** `package.json` has a `"web-types"` field resolving to an
existing `web-types.json`.

**How to verify:**
```bash
node -e "const p=require('./package.json'); const f=p['web-types']; \
  console.log(f ? (require('fs').existsSync(f)?'ok '+f:'DANGLING '+f) : 'FIELD MISSING')"
```

**Pass:** Field present and the file exists.

**Failure mode:** JetBrains IDEs can't auto-discover the component's API
— no attribute completion in WebStorm / IntelliJ.

**Tag:** D-CEM-3.

## C-CEM-7 — Build regenerates the manifest

**Tier:** `[auto]`

**What:** An npm script runs `cem analyze` (directly or via a named
`analyze` script), and `build` depends on it — so the artifacts can't
be built stale.

**How to verify:**
```bash
node -e "const s=require('./package.json').scripts||{}; \
  const all=Object.values(s).join(' | '); \
  console.log(/(cem|custom-elements-manifest)\s+analyze/.test(all)?'analyze wired':'NO analyze step'); \
  console.log(/analyze/.test(s.build||'')||/(cem|custom-elements-manifest)\s+analyze/.test(s.build||'')?'build depends on analyze':'build does NOT run analyze')"
```

**Pass:** An `analyze` invocation exists **and** `build` runs it.

**Failure mode:** Manifest is generated by hand once, then forgotten;
it silently rots as the API changes.

**Tag:** D-CEM-2.

## C-CEM-8 — All three artifacts are packed into the tarball

**Tier:** `[auto]`

**What:** `custom-elements.json`, `web-types.json`, and
`vscode.html-custom-data.json` appear in `npm pack --dry-run` output
(i.e. the `files` field ships them).

**How to verify:**
```bash
npm pack --dry-run --json 2>/dev/null \
  | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>{ \
      const files=(JSON.parse(s)[0].files||[]).map(f=>f.path); \
      ['custom-elements.json','web-types.json','vscode.html-custom-data.json'] \
      .forEach(f=>console.log(f, files.includes(f)?'packed':'MISSING FROM TARBALL'));})"
```

**Pass:** All three present in the tarball listing.

**Failure mode:** The manifest exists locally but never reaches npm —
consumers and the catalog see a package with no custom-element
metadata.

**Tag:** D-CEM-2.

## C-CEM-9 — `keywords` include `web-components` + `custom-elements`

**Tier:** `[auto]`

**What:** `package.json` `keywords` contains both `web-components` and
`custom-elements` (the catalog uses them for search and for grouping
the family into a collection).

**How to verify:**
```bash
node -e "const k=(require('./package.json').keywords||[]).map(x=>x.toLowerCase()); \
  ['web-components','custom-elements'].forEach(t=>console.log(t, k.includes(t)?'ok':'MISSING'))"
```

**Pass:** Both keywords present.

**Failure mode:** The package may still list, but the `web-*` family
can't be grouped as a collection — users find components one at a time
instead of as a suite.

**Tag:** D-CEM-4.

## C-CEM-10 — Manifest is fresh (re-analyzing yields no diff)

**Tier:** `[semi]`

**What:** Re-running the analyzer produces **no change** to the three
artifacts — i.e. the committed / built manifest reflects the current
source.

**How to verify:**
```bash
npm run analyze            # or: npx cem analyze
git diff --stat -- custom-elements.json web-types.json vscode.html-custom-data.json
```

**Pass:** No diff after re-analyzing (D-CEM-2 = A). For D-CEM-2 = B,
diff the freshly generated files against the built ones and confirm
they're identical.

**Failure mode:** Source changed but the manifest wasn't regenerated —
the catalog and editors advertise a stale API.

**Tag:** D-CEM-2.

## C-CEM-11 — Manifest declarations match the source

**Tier:** `[semi]`

**What:** The manifest tells the truth about the element:

1. The declared **tag name** matches
   `customElements.define('the-tag', …)` (same string as C-CST-2 /
   C-NC-1).
2. Declared **attributes** match the `ATTRIBUTE_TABLE` /
   `observedAttributes` (C-NC-7).
3. Declared **events** match the `dispatchEvent` call sites (C-NC-3).

**How to verify:** Read `custom-elements.json`. Cross-check the
`tagName`, `attributes[]`, and `events[]` for the element against the
source (`customElements.define`, `ATTRIBUTE_TABLE`, `dispatchEvent`).
Flag any attribute/event present in source but absent from the
manifest (or vice-versa).

```bash
grep -nE "customElements\.define\(['\"][^'\"]+" src -r
node -e "const m=require('./custom-elements.json'); \
  console.log(JSON.stringify(m.modules?.flatMap(x=>x.declarations||[]) \
    .filter(d=>d.tagName).map(d=>({tag:d.tagName, \
      attrs:(d.attributes||[]).map(a=>a.name), \
      events:(d.events||[]).map(e=>e.name)})),null,2))"
```

**Pass:** Tag, attributes, and events in the manifest match the source.

**Failure mode:** The manifest under-reports (analyzer missed a
dynamically-registered attribute) or over-reports (a removed attribute
lingers). Fix by adding/adjusting `@attr` / `@fires` JSDoc on the
Element class and re-analyzing — **never** by hand-editing the JSON.

**Tag:** D-CEM-1.

## C-CEM-12 — Editor autocomplete actually works

**Tier:** `[manual]`

**What:** In a scratch project that installs the packed tarball, both
editors offer tag + attribute completion.

**How to verify:**
1. `npm pack` the component; `npm i ./<tarball>` into a fresh folder.
2. **VS Code:** add the package's `vscode.html-custom-data.json` to
   `.vscode/settings.json` `html.customData`; open an `.html` file;
   type `<web-…` and confirm the tag and its attributes complete with
   hover docs.
3. **JetBrains (WebStorm / IntelliJ):** open the same project; the
   `web-types` field is auto-discovered from `node_modules`; type the
   tag and confirm attribute completion.

**Pass:** Both editors surface the tag, its attributes, and hover docs.

**Failure mode:** The files ship but don't wire up — usually a wrong
`outdir`, a malformed `html.customData` path, or a `web-types` field
pointing at the wrong file. Autocomplete is the payoff; verify it once
per package after the first wiring, then on any analyzer-config change.

**Tag:** D-CEM-3.

## C-CEM-13 — Public-facing members carry harvestable `/** */` JSDoc

**Tier:** `[semi]`

**What:** The manifest (and editor autocomplete) is only as useful as
the descriptions the analyzer can harvest. Every public-facing
attribute / property the element advertises must have a description the
analyzer can actually read, which requires **both**:

- **(A) Coverage.** Each backing member of the public options
  interface — the members targeted by the `key:` column of
  `ATTRIBUTE_TABLE` (C-NC-7), the members behind public property
  setters, and any `@attr` the class declares — carries a description.
  Enum-valued members additionally document their **allowed values**
  (e.g. `single` | `range` | `multiple`).
- **(B) Format.** The description is a JSDoc `/** … */` block
  immediately preceding the member. **Inline `//` line comments and
  trailing `//` comments are NOT harvested** by the analyzer (nor
  surfaced by TypeScript hover), and a bare member has nothing to
  harvest.
- **(C) Canonical shape.** Enum / union members follow the canonical
  property-JSDoc format from
  [custom-elements-manifest.md](./custom-elements-manifest.md) →
  "Canonical property-JSDoc format": an **intro line** (ending
  `Default: <value>.` when defaulted), a **blank line**, then **one
  bullet per allowed value** (`` - `value` — description ``). The blank
  line is load-bearing — without it the hover collapses the list into
  the intro paragraph.

Put the doc as `/** */` on the interface member, not on the attribute
wiring — one source then feeds both TypeScript consumers and the
manifest.

**How to verify:**

1. Find the public options interface(s) — the type whose members are
   the `key:` targets in `ATTRIBUTE_TABLE` (e.g. `DatePickerOptions` in
   `src/types.ts`).
2. For each member that backs an observed attribute or public property,
   confirm a `/** */` block immediately precedes it. Flag bare members
   and `//`-commented members.

```bash
# Smell test: trailing or standalone // comments on the options interface —
# these won't reach the manifest. Point at the interface's file.
grep -nE "^[[:space:]]*[A-Za-z_].*:.*//" src/types.ts    # trailing // on a member
grep -nE "^[[:space:]]*//"                 src/types.ts    # standalone // near members
```

3. For enum unions, confirm the allowed values are documented (a list
   in the member's JSDoc, or per-value JSDoc on the union type) so the
   editor can surface them.

**Pass:** Every public-facing member has a preceding `/** */` block with
a meaningful description; enum members document their values in the
canonical intro-line + blank-line + bullet-list shape. No public member
relies on a bare declaration or an inline `//` comment for its
description.

**Failure mode:** Attributes list in autocomplete with an empty hover —
e.g. `selection-mode` shows no description because its backing member
`selectionMode?: 'single' | 'range' | 'multiple'` in `types.ts` had no
`/** */` block, while `date-member` / `picker-mode` / `time-display`
(which do) show hover text. Inline `//` comments create a false sense
of "documented" — they never reach the manifest or TS hover.

**Fix:** Convert inline `//` / bare members to `/** */` JSDoc on the
backing interface member, then re-run `cem analyze` (see C-CEM-10).

**Tag:** D-CEM-3.
