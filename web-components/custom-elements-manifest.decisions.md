# Custom Elements Manifest — Pre-Implementation Decisions

Answer every decision below **before** wiring a Custom Elements
Manifest into a package. Each has a recommended default; deviating
requires a one-line justification in the PR description or the
component README.

Read [custom-elements-manifest.md](./custom-elements-manifest.md) first
if any of these questions don't make sense.

---

## D-CEM-1 — Applicability

**Question:** Does this package ship custom elements?

**Options:**

- **A — Web-component (custom element).** The package calls
  `customElements.define(...)` and is consumed as a custom element
  (`@keenmate/web-grid`, `@keenmate/web-daterangepicker`, …). The
  full triad applies. This is the default for every `web-*` package.
- **B — Svelte / light-DOM component.** Consumed as a Svelte component,
  no `customElements.define(...)`. **The whole triad is N/A** — mark
  every C-CEM-* as N/A and note "no custom elements" in the PR.
- **C — Dual build (Svelte *and* a custom-element target).** The
  package ships a `customElements.define(...)` build in addition to the
  Svelte entry. The CEM applies to the **custom-element build's**
  entry points; point `customElements` at that manifest. Treat as A
  for this topic.

**Default:** A for `web-*` packages, B for `svelte-*` packages.

**Don't:** skip the CEM on a web-component because "it's just for
editors" — the webcomponents.org listing depends on it too.

## D-CEM-2 — Where the generated artifacts live in git

**Question:** Are the three generated files (`custom-elements.json`,
`web-types.json`, `vscode.html-custom-data.json`) committed to the
repo, or gitignored like `dist/`?

**Options:**

- **A — Committed and regenerated by build (default).** The files are
  tracked; `npm run build` regenerates them; `/publish` stages them
  (Section 14). Small metadata files, and their diff is a
  human-readable API-change record surfaced in every PR review —
  which is also how C-CEM-10 (freshness) stays honest without a
  separate CI build step.
- **B — Gitignored, generated at build, shipped via `files`.** No git
  churn, but API changes are invisible in PR review, and freshness
  (C-CEM-10) must be enforced by a CI build-and-diff step. Choose this
  only if the build is fully deterministic and a CI freshness gate is
  already in place.

**Default:** A. The files are tiny and the reviewable diff is worth
more than avoiding the churn.

**Don't:** treat these like `dist/`. `dist/` is gitignored because it's
large and bundler-specific; the CEM artifacts are small, stable, and
their diffs are useful.

## D-CEM-3 — How the editor files are generated

**Question:** How are `vscode.html-custom-data.json` and
`web-types.json` produced?

**Options:**

- **A — Analyzer plugins in `custom-elements-manifest.config.mjs`
  (default).** `customElementVsCodePlugin` and
  `customElementJetBrainsPlugin` run as part of `cem analyze`, so one
  command emits all three artifacts and they can never drift from the
  manifest.
- **B — Separate generator scripts.** A distinct npm script per editor
  file. Acceptable only if a plugin is incompatible with the toolchain;
  the scripts MUST run as part of `build` so all three stay in lockstep.

**Default:** A. One command, no drift.

**Don't:** hand-write either editor file. They're derived from the CEM;
hand edits are wiped on the next generation.

## D-CEM-4 — Catalog & collection metadata

**Question:** How does the package advertise itself to the
webcomponents.org catalog and its collection grouping?

**Options:**

- **A — Family keywords + description (default).** `keywords` include
  `web-components` and `custom-elements` plus the family markers
  (`keenmate`, `bliss`), and the `package.json` `description` names the
  component. The catalog indexes and groups on these. This is the
  minimum for a listing and for the family to surface as a collection.
- **B — A + an explicit collection registration.** In addition to A,
  the family is registered as a named collection on webcomponents.org
  (a coordination move done once for the whole `web-*` suite, not
  per-package). Track the collection slug in the suite's shared docs.

**Default:** A per-package; B once for the suite (coordination move —
flag it, don't do it silently per component).

**Don't:** drop the `web-components` / `custom-elements` keywords —
without them the catalog can't group the family.
